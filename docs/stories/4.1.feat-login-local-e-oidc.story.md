# Story 4.1: Página de login com intranet (OIDC) e usuário local

## Status

InReview

## Story

**Como** administrador do BulkMail Pro,
**quero** entrar pela página `/login` usando a intranet do CREFITO 11 (OIDC) ou um usuário e senha locais,
**para** acessar o sistema mesmo quando a intranet estiver indisponível ou quando eu não tiver conta nela.

## Acceptance Criteria

### Página `/login`

1. Qualquer rota protegida acessada sem sessão redireciona para `/login?next=<rota original>`; usuário já autenticado que abre `/login` vai para `next` (ou `/`).
2. `next` só aceita caminhos internos (`/algo`); valores externos (`//host`, `https://...`, `/\host`, caracteres de controle) ou que apontem para `/login` são trocados por `/`.
3. A página exibe um cartão com faixa superior `slate-900` contendo o logo completo do CREFITO 11 (versão negativa), o botão escuro **"Entrar no login intranet"** com o símbolo do CREFITO 11, o divisor "ou" e o formulário de usuário e senha.
4. O botão da intranet leva a `/api/auth/oidc/login?next=<next>`; após o callback OIDC bem-sucedido o usuário volta para `next`.
5. Falhas do callback OIDC redirecionam para `/login?auth_error=<código>` e a página mostra a mensagem correspondente.
6. Respostas `401` de qualquer endpoint da API (exceto `/api/auth/*`) durante o uso levam a `/login?next=<rota atual>`.

### Login local

7. `POST /api/auth/local/login` com `{ username, password }` cria uma sessão local e o cookie de sessão; exige `Origin` igual a `APP_ORIGIN`.
8. O nome de usuário é comparado sem diferenciar maiúsculas/minúsculas e sem espaços nas pontas.
9. Credenciais inválidas, usuário inexistente ou desativado retornam `401` com a mesma resposta genérica (`invalid_credentials`) e tempo de resposta equivalente (verificação de hash simulada para usuário inexistente).
10. Após 5 falhas para o mesmo par usuário+IP, ou 20 falhas do mesmo IP, em 15 minutos, novas tentativas retornam `429` (`too_many_attempts`) sem verificar a senha; um login bem-sucedido zera o contador do par usuário+IP.
11. Senhas são armazenadas com `scrypt` (Node `crypto`, sal aleatório de 16 bytes, N=16384, r=8, p=1, chave de 64 bytes); a política exige de 12 a 128 caracteres.
12. Cada tentativa local gera um log `[LocalAuth]` com resultado (`success`/`failure`/`blocked`), usuário normalizado, IP e motivo — nunca a senha.
13. `LOCAL_LOGIN_ENABLED=false` oculta o formulário (via `GET /api/auth/options`) e faz `POST /api/auth/local/login` responder `404`. Padrão: `true`.

### Sessão

14. Sessões passam a ter `provider` (`oidc` ou `local`). Sessões existentes no Redis sem `provider` continuam válidas como `oidc`.
15. Sessão local dura 8 horas fixas, sem renovação no provedor OIDC; o logout local apenas encerra a sessão e volta para `/login` (sem logout da intranet).
16. `GET /api/auth/me` retorna o usuário com `provider`; o menu da conta mostra o nome de usuário local.
17. Usuário local e usuário OIDC têm o mesmo acesso (sem perfis).

### Administração do usuário local

18. Migration cria `local_users` (`id` uuid, `username` único em minúsculas, `password_hash`, `disabled_at`, `last_login_at`, `created_at`, `updated_at`).
19. `npm run user:admin -- create --username=<nome>` pede a senha duas vezes sem eco no terminal e cria o usuário; recusa se já existir. Não existe senha padrão.
20. `npm run user:admin -- reset-password --username=<nome>` troca a senha; `disable`/`enable` desativam/reativam. `reset-password` e `disable` encerram imediatamente as sessões locais ativas daquele usuário.
21. Nomes de usuário válidos: 3 a 64 caracteres em `a-z`, `0-9`, `.`, `_`, `-`.

### Infraestrutura

22. O número de proxies confiáveis do Express é configurável por `TRUST_PROXY_HOPS` (padrão `1`), para que o IP usado no limite de tentativas seja o do cliente real atrás de Traefik + Nginx.
23. O runbook `docs/production.md` documenta criação do admin, reset, desativação e a verificação do IP real.

## Dev Notes

- Sessões ficam no Redis (`backend/src/services/authSessionService.ts`), prefixo `oidc:session:`; o prefixo é mantido para não invalidar sessões existentes.
- Cadeia de proxies em produção: Traefik → Nginx (frontend) → backend. O Nginx acrescenta `$remote_addr` ao `X-Forwarded-For`.
- O build do frontend usa `frontend/` como contexto Docker; o logo precisa ser copiado para `frontend/src/assets/`.
- O frontend não possui runner de testes unitários; o comportamento de UI é coberto por Playwright com API simulada (`page.route`).
